Crash → resume → replay → fork → audit

Matching the batch id alone would only prove the plan agreed. The content hash is what proves the tokens, masks and position ids were the same — it is the check that caught a real bug here, when replayed SFT samples lost their prompt masking because role spans were missing from the ledger.

  1. crash step 68 a real exception mid-step, after records were appended and before the next checkpoint — so the rewind has something to discard 18 ledger records discarded
  2. resume from ledger offset 120 recovery coordinate is the ledger offset, not the step number. The expected next batch id was recorded before the crash and asserted after. next batch matched: True · no repeats True · no skipped steps True · offsets dense True
  3. replay steps [20, 40] re-served from the ledger, never recomputed from the planner. Compared on batch_id, batch_content_hash, loss_mask_hash, token_spans, shard_ids. 20/20 matched · 0.304s
  4. fork exp-b at step 40 new branch id from the parent checkpoint; the parent's records must be byte-unchanged afterwards. distinct batches True · parent intact True · starts at divergence True
  5. audit 48 shards in window which shards trained the model between two token counts, and which OPUS decisions preceded the largest loss spike. 52194 loss-bearing tokens · spike 0.742 at step 73
