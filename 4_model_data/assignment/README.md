# Session 4 assignment — data cleaning widget

A real Python cleaning pipeline (8 stages, plus a hashed stage 0 that draws the
samples) run against **two** corpora, plus a static widget that presents the
results.

Every number the widget shows is generated by `pipeline/run_all.py` into
`results.json` — nothing on the page is hand-typed or illustrative.

## Why two corpora

One corpus could not exercise all eight strategies, and a widget reporting
three zeroes is a worse answer to "what was cleaned" than a second corpus costs.

| | `telugu_web` | `reasoning_sft` |
|---|---|---|
| Source | `ai4bharat/sangraha`, `unverified/tel` | 4 reasoning/SFT sets from the `lordx64` profile |
| Size | ~11.6k docs / 50.0M tokens | ~9.6k docs / 12.0M tokens |
| Exercises | Brahmic joiner preservation, the `te`/`tel` language-code bug, Indic quality-filter bias, Indic PII | ghost-tag unification, cross-source dedup, code-aware cleaning, license gating |
| Cannot exercise | ghost tags (a web crawl has no conversation markers), cross-shard dedup (single source) | Indic-specific anything |

The SFT sources ship **pre-flattened text with literal ChatML markers already in
the published `text` field**, which is what makes the ghost tags genuine rather
than something our own ingestion script introduced. Two of the four sources
(`fable-sft-combined-v2` and `agentic-distill-fable-5-sft`) overlap
byte-for-byte — verified before the design was committed to — which is what
makes cross-source deduplication a measurement rather than a diagram.

## Reproducing

```bash
python -m venv .venv
source .venv/Scripts/activate   # or .venv/bin/activate on macOS/Linux
pip install torch --index-url https://download.pytorch.org/whl/cpu
pip install -r requirements.txt
cd pipeline
python stage0_sample.py          # re-draw both corpora from Hugging Face
python run_all.py                # all corpora, each run twice
python analysis_duplicate_structure.py
```

Stage 6 loads a real NER model per corpus (Telugu and English) and runs it over
every document; stage 4 trains a real `scikit-learn` classifier at the start of
each Telugu run. The pipeline runs **four** full passes (two corpora × two
determinism runs), so expect **~3 hours** on CPU, not seconds — it prints
per-stage progress as it goes.

Regenerate the widget's data file afterward:

```bash
python build_site_data.py
```

It merges `results.json` with `analysis_duplicate_structure.json` into
`site/data.js` and prints a summary of what it wrote.

## Viewing the widget locally

`site/` is fully static and self-contained (no build step, no external requests
at runtime). Open `site/index.html` directly, or serve it:

```bash
cd site
python -m http.server 8000
```

## What's real vs. what's a stand-in

Both of the stand-ins an earlier review flagged are now real: the quality
filter's layer 2 is a genuine `scikit-learn` `LogisticRegression` trained on
`pipeline/quality_labels.jsonl`, and the PII stage runs a real NER model
alongside the gazetteer rather than instead of it.

What remains honestly disclosed:

- **Extract is a verification pass on the Telugu corpus.** Sangraha's
  `unverified` tier ships pre-extracted plain text; there is no HTML to extract
  and pretending otherwise would be theatre. On the SFT corpus the stage does
  real work, masking code spans so the markup stripper cannot corrupt them.
- **The quality classifier does not run on the SFT corpus.** Its labels are 200
  Telugu web documents. They say nothing about English reasoning traces, so
  layer 2 is skipped and reported as `SKIPPED` with its reason rather than run
  to produce a number that would look like a measurement.
- **The NER layer reads the first 1,000 characters of each document.** That is a
  real recall limit; the widget reports what share of corpus text it leaves
  unscanned rather than mentioning it in passing. Regex layers cover 100%.
- **Telugu deduplication removes nothing, and that is a finding rather than a
  failure.** Round 1 drew a uniform random ~8% sample, which keeps both halves
  of a duplicate pair with probability p² (~0.6%) and therefore could not have
  found duplicates whether or not they existed. The draw is now contiguous,
  which removes that artifact — and the result did not change. So
  `analysis_duplicate_structure.py` sweeps the threshold down to 0.3 and reports
  the curve: still zero at 0.6, a handful of pairs by 0.5. A flat curve well
  below the operating threshold is the evidence that the corpus is clean rather
  than the detector blind. The prediction that contiguous sampling would surface
  Telugu duplicates was wrong, and is reported as wrong.

## Round 2: what changed after review

An external review of round 1 confirmed the strategy count and the honesty of
the disclosures, and raised seven issues. All were addressed except the Netlify
deploy, which was descoped by the user.

1. **Three of eight strategies had nothing to act on** → second corpus added.
2. **Sampling destroyed duplicate pairs** → contiguous slices (see the honest
   outcome above).
3. **No script recorded how the sample was drawn** → `stage0_sample.py`, hashed
   into the manifest with the other stages.
4. **The determinism check could not fail** → run 2 now executes in a separate
   interpreter with a different `PYTHONHASHSEED`. Two passes in one process
   share a hash seed, so any dependence on set iteration order would have
   reproduced identically and passed while proving nothing.
5. **One manifest for the whole corpus** → one per shard, with a license gate
   that blocks rather than warns. Three of the four SFT sources fail it: one
   declares no license, two are AGPL-3.0.
6. **NER truncation disclosed but not quantified** → measured and charted.
7. **Two overstatements corrected** → "Session 3 discussed Sangraha at length"
   (it appears once, in a list), and the unqualified token count (cl100k gives
   Telugu a fertility of ~13 tok/word; an Indic tokenizer would put the same
   corpus below the assignment's 10M floor).
